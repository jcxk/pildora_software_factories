NIVEL 1

Lo que ya sabéis: empaquetar una app

📦
Imagen
La receta congelada: tu app + sus dependencias. Inmutable, versionada, compartible.
🚂
Contenedor
Una imagen en ejecución. Aislada, ligera, desechable: muere y renace igual.
📜
Dockerfile
Las instrucciones para construir la imagen, capa a capa.
$ docker build -t mi-app . $ docker run -p 8000:8000 mi-app

Un contenedor = un proceso empaquetado.
Tu máquina no se contamina de dependencias.
La de tu compañero tampoco: «en mi máquina funciona» se acabó.

⏱ ~4' · Recap voluntariamente corto: ya lo vieron la charla anterior. Pregunta a la sala: «¿quién ha hecho ya un docker run?» — calibra el nivel real. IDEA CLAVE que hay que dejar caer: un contenedor es UN proceso. Esa frase es la semilla de toda la charla: si tu app son varios procesos… necesitas varios contenedores.
NIVEL 1

…hasta que tu app crece

Una app de verdad no es un proceso: es web + API + base de datos + caché. A mano:

$ docker network create red $ docker run -d --name db --network red -e MYSQL_PASSWORD=*** -v datos:/var/lib/mysql mysql:8.4 $ docker run -d --name cache --network red redis:7 $ docker run -d --name api --network red -e DB_HOST=db -e REDIS_HOST=cache mi-api $ docker run -d --name web --network red -p 8080:80 mi-web # …y al día siguiente: IPs cambiadas, orden de arranque, variables a medias…

🔢

🔁

⏱ ~9' · Definición visual. La definición formal en una frase: «una arquitectura de muchas piezas pequeñas, cada una con UNA responsabilidad, que se despliegan y escalan por separado y se comunican por red». Subraya: por RED, no por llamadas de función. Eso cambia TODO lo demás (lo veremos en «qué pagas»). Ni una palabra más de teoría: el contraste visual ya lo dice.
NIVEL 2

Qué ganas

🎚️
Escalar solo lo que sufre
¿La API va saturada? Más réplicas de la API. El resto, quieto.
🚀
Desplegar por partes
Cambia la API sin tocar la web. Sin «redeploy total» a las 2 AM.
👥
Equipos autónomos
Cada equipo posee sus piezas: sus ritmos, sus despliegues.
🧩
Mezclar tecnologías
Python para la API, Redis para caché, MySQL para datos: cada pieza, su herramienta.

…y fallos más acotados: se cae la caché, la app sigue (degradada, pero viva).

⏱ ~11' · Vende el sueño antes de la factura. Ejemplo cercano: «la web de matrículas en época de matrícula: solo necesitas más réplicas del frontend y la API de pagos, no de todo». CORTABLE si va tarde: puedes comprimir a dos ítems (escalar y desplegar por partes).
NIVEL 2

Qué pagas (la factura siempre llega)

📡
Red y latencia
Llamada de función: nanosegundos. Llamada por red: milisegundos. Y se pierde.
⚙️
Más piezas vivas
4 servicios = 4 cosas que arrancar, vigilar, actualizar y romper.
🧨
Fallos parciales
¿La caché no responde? La app entera debe saber qué hacer sin ella.
🔍
Verlo todo es más difícil
Un fallo repartido entre 4 contenedores y 3 equipos = detective work.

La consistencia también se paga: datos repartidos = sincronizar es TU problema.

⏱ ~13' · LA diapositiva honesta. Esta transparencia te da credibilidad delante de juniors: el mundo está lleno de seniors que solo enseñaron la cara A. Frase para la sala: «los microservicios intercambian complejidad de código por complejidad de operaciones». Que se la lleven apuntada. CORTABLE: dos ítems (red y piezas vivas) si el reloj aprieta.
NIVEL 2

¿Cuándo bajar a este nivel?

Sí, cuando…

  • El dominio es grande y se parte en trozos naturales
  • Partes del sistema necesitan escalar distinto
  • Equipos múltiples que se pisan en un mismo repo
  • Requisitos distintos por pieza (tiempo real vs batch)

Todavía no, si…

  • El producto acaba de nacer y aún no sabes qué tiene
  • El equipo es pequeño (¡como el vuestro en los proyectos!)
  • «Porque lo llevan las empresas grandes» — no es un requisito

Regla de oro: empieza con un monolito bien modularizado; sepáralo cuando duela.

⏱ ~15' · Consejos reales para su nivel: en los proyectos de F5, un monolito modular bien hecho vale más que 6 microservicios mal cortados. «Doler» = despliegues bloqueados, escalado desigual, equipos pisándose. El pie de regla de oro es EL mensaje del nivel 2. Repítelo dos veces.
NIVEL 2

La herramienta del nivel 2: Docker Compose

Un archivo describe toda la app.
Un comando la levanta entera.

$ docker compose up -d

Red privada + DNS interno + orden de arranque + volúmenes + variables: todo, declarado.
Nada de flags de memoria.

services: web: build: ./web ports: ["8080:80"] api: build: ./api environment: DB_HOST: db # ¡DNS! db: image: mysql:8.4 volumes: [datos:/var/lib/mysql]

Compáralo con la transparencia de los 5 docker run…

⏱ ~17' · El alivio tras el dolor. Contraste explícito: vuelve con el mando a la diapositiva 5 un segundo — «cinco comandos ilegibles → un YAML que se lee como una lista de la compra». Señala DB_HOST: db en el YAML: «la api conecta con la base de datos POR NOMBRE. ¿Quién traduce nombre → IP? Compose. Lo veréis en la práctica con vuestros ojos.» La versión completa anotada está en el repo (demo/compose.yml).

NIVEL 3

Qué cambia al crecer

🫀
Healthchecks
Cada servicio declara cómo comprobar que está vivo. Compose espera a eso antes de arrancar a los siguientes.
📈
Escalado
--scale api=3: réplicas de un servicio sin tocar los demás.
🎭
Dev vs prod
overrides y profiles: un YAML base + extras por entorno.
🧭
¿Y más profundo?
Cuando Compose se queda corto: orquestadores — Swarm, Kubernetes… otro día.

Todo esto ya está sembrado en el compose.yml del repo: healthchecks incluidos.
